# 07. 적재 파이프라인 (M3)

조사 엑셀을 읽어 survey 그래프(TTL)로 만드는 단계의 기록. 설계 기준은 `docs/02` 5·6장, 규칙 세부는 골든
interpretations(I1~I33). 합성 데이터로만 개발·시험했다.

## 1. 쓰는 법

```bat
python -m engenius_onto load                 :: data/synthetic/survey → output/<실행ID>/ (사내: --data real)
python -m engenius_onto push                 :: 최신 실행의 survey.ttl + 스키마 OWL 을 Fuseki named graph 로 교체
python -m engenius_onto apply-review output\<실행ID>\tool_review.csv   :: 툴 통합 판정을 config 에 반영
python -m engenius_onto template-examples --form <양식.xlsx>          :: 사내 양식의 예시 행을 config 로 추출
```

| 산출물 | 내용 |
|---|---|
| `output/<실행ID>/survey.ttl` | survey named graph — 분야·툴·분류·툴사용·입출력·적재 기록(SurveyLoad) |
| `output/<실행ID>/load_log.json` | 파일별 건수, 제외 행과 사유, 경고, 행 단위 스키마 검증, 툴 통합 후보·속성 엇갈림, 조사 누락 후보, 레지스트리 요약, SHACL 결과 |
| `output/<실행ID>/tool_review.csv` | 툴 통합 후보 검토표 (엑셀에서 열림) — '판정' 열에 통합/별개 |
| `data/<synthetic\|real>/registry/*.csv` | FLD·TOOL·USE·CAT ID 레지스트리 (제자리 갱신, 상태 열 포함) |

SHACL 검증은 `FUSEKI_HOME`·`JAVA_HOME` 이 잡혀 있으면 자동으로 돈다 (Fuseki jar 의 Jena, 추가 반입 없음). 위반은
적재를 막지 않고 경고 보고서로 남는다 (D4).

## 2. 구성

| 모듈 | 역할 |
|---|---|
| `form_spec.py` | 양식 열 명세 — 헤더 문구·필수·선택지 목록·셀 종류를 **스키마의 form_* 주석에서** 읽는다 |
| `normalize.py` | 툴 이름 키(I1·I2·I14), 연계 SW명 분리(I16·I17), 확장자(I12 — `형식명(.확장자)`·비확장자 토큰·다중 점), 인명 유사 판정 `looks_person`(I29) — 값은 config |
| `loader.py` | xlsx 읽기, 재발송(I33), 헤더 매핑(I30), 예시 행(I15), 셀 규칙(D5·I27), 필수·선택지(I28), 인명 패턴(D6·I29), 중복·고아, 툴 통합·후보(I23), 입출력 표시 키(D2) |
| `registry.py` | ID 레지스트리 CSV — 키 규칙(D3), 폐기·통합됨 상태(D7) |
| `rdf_writer.py` | 전용 RDF 작성기 — 이름에만 @ko, 원문 리터럴 보존(D4), 속성 IRI 는 스키마에서, IO 해시 ID(D2) |
| `survey_load.py` | 실행 전체 — 행 단위 Pydantic 검증, SHACL, 산출물, 검토표 판정 반영 |

설정 (`config/`, 사내 양식이 다르면 여기만 고친다):

| 파일 | 내용 |
|---|---|
| `rules.yaml` | 파일명 규칙, 헤더·데이터 시작 행, 빈 행 끝 판정, 인명 패턴, 빈 값 토큰, 버전 토큰, 연계 SW 구분자, 도출 규칙 값(M4) |
| `extensions.yaml` | 확장자 별칭(한글·영문 표기), 사내 표기 토큰, 구분자, 확장자 패턴(숫자만 있는 토큰 제외), 비확장자 토큰 `non_extension_tokens`, 묶음 확장자 `compound_extensions` (2026-10-12, docs/09 #10) |
| `header_map.yaml` | 헤더 **추가 문구**만 (기본 문구는 스키마 form_header) — docs/02 9장의 '전체 매핑' 에서 바꿨다: 매핑이 스키마 한 곳에 있어야 양식 매핑 검사(M1)와 적재기가 어긋나지 않는다 |
| `template_examples.yaml` | 예시 행 — 원본 양식에서 추출 (`template-examples` 명령, 테스트가 양식과 일치 검사) |
| `tool_aliases.yaml` | 툴 통합 판정 누적 (aliases·distinct) |

## 3. 스키마 v0.2

- 파생 클래스 `Reconciliation`(입출력·상대 툴·판정), `IsolationFinding`(툴사용·유형) — D1 대로.
- **`Handoff`(착수 구간) 추가 — D1 구체화, Leo 확인 필요 (M4 멈춤 때).** D1 은 착수 등급을 Reconciliation 에 두기로
  했으나, 같이 승인된 D1-2(변환 구간을 상대 툴의 사용마다 펼침) 때문에 한 대조 결과에 등급이 여럿 생긴다 — 합성 데이터에서도
  CATIA 두 사용이 A·B 로 갈린다. 그래서 착수 순위 1행 = (공급 툴사용, 수요 툴사용, 종류: 수기·변환·비고) 에 등급·근거
  입출력·순위를 두는 클래스를 따로 뒀다. 골든 handoff_ranking 과 1:1 이고, 보고서 시트 2 와 M6 `manual_handoffs` 의 원천이다.
  Reconciliation 에는 등급을 두지 않는다.
- `grade`·`supplier`·`consumer` 를 Feed 전용 속성에서 공용 슬롯으로 올려 Feed·Handoff 가 같이 쓴다 (IRI 불변).
- `DataCategory.status` 추가 — D7 은 분류도 폐기 상태로 계속 내기로 했는데 v0.1 에 슬롯이 없었다.
- 노드 선택지 목록 주석 `form_list` (담당 부서 → 담당부서, 분류 → 온톨로지분류) — 적재기의 선택지 검사가 스키마에서 읽는다.

- **입출력 77건·툴사용 34건을 참조 계산과 한 건씩 대조** — 표시 키·소유·분류·정규화 확장자·사내 표기·연계 해석·등급 입력값 전부 같음.
  적재기는 엑셀 층(헤더 셀·셀 타입·예시 행 위치)을 읽고 참조 계산은 명세를 읽으므로 서로 독립인 두 구현이다.
- **스키마 층 검증 두 가지가 같은 5건을 찾는다**: 행 단위 Pydantic 과 Jena SHACL 모두 PERF-02 만료 시기 형식, TEST-05 조작 방식·자동화
  인터페이스 누락, MATLAB 조작 방식 선택지 밖, TURB-03 전달 방법 '메일' — 전부 적재 경고와도 대응한다. 분류 '보고서/문서'·'설계-2D
  Layout' 은 노드라 SHACL 위반이 아니고 적재 경고로만 잡힌다 (의도).

## 5. 한계·다음

- 합성 파일은 openpyxl 로 만들어 실제 Excel 저장본과 다르다 (B 열 수식 캐시값, 데이터 유효성 형식). 적재기는 둘 다 쓰지 않는다 —
  실제 회신 파일 첫 적재 때 헤더 경고·예시 행 제외 건수를 먼저 본다.
- 같은 입출력 행에 같은 미조사 툴을 두 번 적으면 RDF 는 한 번만 남는다 (집합). 조사 누락 후보의 언급 횟수는 행 단위로 센다.
- 파일명이 규칙 밖이면 분야를 몰라 재발송 판정·담당 부서 대조를 하지 않는다 (경고).
- 다음 = M4: 도출 규칙(SPARQL CONSTRUCT)으로 Feed·Reconciliation·IsolationFinding·Handoff 를 derived 그래프에 만들고,
  골든(Feed 71·대조 103·착수 15행 등)과 대조, 보고서 10시트 + 툴 연결 지도(HTML, 오프라인). 끝나면 Leo 확인 ②.

## 6. 독립 검토 결과 (2026-09-24) — 수리는 다음 세션

#25 는 a~d 로 나눠 셌다). 합성 데이터에서는 전부 통과하지만 실제 Excel 회신·사내 양식 변형·인명이 섞인 파일명에서 드러나는 결함이다.
정본과 수리 계획(대상 파일·회귀 테스트·골든 영향·Leo 결정 질문·작업 순서)은 **`docs/09_M3_검토_수리계획.md`**. 요지:

- **가장 큰 것 3가지**: ① 파일 간 같은 (담당 부서, SW ID) 가 한 노드로 무경고 병합 (#1 — 부서 간 협업 행, 파일명 표기가 다른 재발송,
  '(1)' 복사본, 빈 담당 부서 + 숫자 SW ID 전부 재현) ② 파일명·식별자 칸의 인명이 survey.ttl·레지스트리·로그로 감 (#8·#20·N1 —
  절대 규칙 5) ③ read_only 읽기의 병합 셀·잘못된 dimension·빈 행 10개 뒤 행 소실 (#4·#5·#6).
- 이 문서 4장의 "골든과 같음" 은 그대로 유효하다 — 지적은 골든 밖 입력에 대한 것이고, 수리 계획은 전부 골든 값을 바꾸지 않게 잡았다
  (#10 확장자 규칙과 #21 은 해석 I12·I16 개정과 oracle 동반 수정이 필요하지만 현재 골든 값은 불변으로 측정).
- 수리 전에는 **실데이터를 적재하지 않는다** (특히 L1 인명 묶음). M4 골든에 영향을 줄 수 있는 L2~L4 는 M4 착수 전에 끝낸다.

## 7. M3.1 2차 잔여 검증 기록 (2026-10-12~)

- **#10 확장자 정규화** (docs/09 #10, Leo 결정 2026-10-12): `형식명(.확장자)` 는 괄호 안 확장자(앞 한 단어는 버림, 공백 허용) · 영문 별칭 excel/word/powerpoint ·

  수정 요청표 '확장자 확인'. 공통 인명 가림 헬퍼(`Normalizer.looks_person`·`Loader._q`·`PERSON_MASK`)를 처음 만들어 확장자 경고에 쓴다 (칸이 인명 유사면 토큰·값 대신 가림 문구).
  적재기(정규식)와 oracle(괄호 훑기)을 따로 구현해 사례 52건·명세 값 31종 일치(`tests/test_loader_m31_3.py` A절), 무작위 20만 입력 대조 불일치 0.
  골든 값 불변 (I12·I13 문구만 개정) — 합성 수정 요청표에만 TEST-05 '또는' 칸의 '확장자 확인' 1행이 더해진다.
  실데이터 첫 재적재에서는 `Excel(.xlsx)`·`Word` 같은 표기의 정규화 확장자가 바뀌고(IO ID 는 원문 기준이라 그대로), '확장자 매핑 실패' 가 늘 수 있다.
