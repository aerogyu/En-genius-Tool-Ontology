# 10. 조직 단위 = 파트 (설계 제안, 2026-09-28 — Leo 확인 대기)

Leo 가 실제 조사 파일을 받아 본 결과, 응답 단위(담당자)는 **파트 23개**이고 양식의 '담당 부서' 드롭다운(10개)과 개수가 다르다.
Leo 방향: **파트 단위로 나눠야 부서 간 온톨로지가 잘 붙는다** (예: CD 형상설계팀 → CDT(터빈)·CDC(압축기) 로 분할 요청 예정).
이 문서는 그 방향을 스키마·적재·파일명에 어떻게 반영할지의 제안이다. 확정되면 M3.1 묶음 T(`reference/양식_v1.1_변경분.md` 5장)에 넣는다.

## 1. 결론 먼저

- **개수가 달라도 된다.** 온톨로지의 조직 노드(`ResearchField`, RDF `eg:Field`, ID `FLD-nnn`)를 **파트**로 정의하면 그만이다.
  '담당 부서' 드롭다운 값(10개)은 파트의 **분류 속성**으로 남긴다 (묶어 보기·집계용).
- DB 비유: `parts` 테이블 23행(PK = 무의미 FLD ID, 자연키 = 파트 약칭) + 분류 컬럼 `domain`(10값). 조사 파일은 파트당 1개.
- 상위 스키마 v0.2 §9 가 이미 이렇게 돼 있다 — 조직은 노드, 이름은 속성, 개명은 라벨 갱신, **분할은 새 노드 + 승계(succeeded_by)**.
  CD·FEM 분할은 이 승계 엣지로 표현되므로 분할 전에 적재해도 ID 체계는 깨지지 않는다.

## 3. 설계 (M3.1 묶음 T, 스키마 v0.3)

1. **`config/parts.yaml`** (신설, 초안은 이미 있음): 약칭 → 정식 이름, 허용 '담당 부서' 값, 상태, 승계(`succeeds: [CD]`). 사내에서 편집.
   FLD 노드의 라벨은 정식 이름, `skos:altLabel` 에 약칭. ID 는 지금처럼 레지스트리가 발급하는 무의미 번호.
2. **파일명**: 규칙은 그대로 `Tool조사_<파트약칭>_<YYYYMMDD>.xlsx` (docs/02 5-1 의 `<부서>` 자리에 약칭). ASCII 라 괄호·공백 문제가 없다.
   약칭 미정 파트 2개는 약칭이 정해진 뒤 이름 붙인다 (급하면 임시 코드로 적재하고 #25b `field_renames.yaml` 로 개명).
3. **적재기**: FLD 키 = **파일명의 파트 약칭** (지금은 행의 '담당 부서' 값). 행의 '담당 부서' 는 새 슬롯 `domain`(가칭, 열거형 = 드롭다운 10개)에
   저장하고 parts.yaml 의 허용 값과 다르면 경고만. Tool ID 접두어가 파일 파트와 다르면(예: CDT 파일에 CD-01) 경고만 — 값은 보존.
   docs/09 #1 의 '파일 간 같은 (담당 부서, SW ID)' 충돌은 파트가 키가 되면 구조적으로 사라진다 (#1 (A) 의 `@파일분야` 접미는 안전망으로 유지).
4. **분할(CD→CDT/CDC/…, FEM→…)**: 분할된 파일이 오면 옛 FLD 'CD' 는 status 폐기 + `succeeded_by` 새 FLD 들 (parts.yaml `succeeds`).
   분할 파일이 안 오면 CD 한 노드로 간다 — 그 세 파트 **사이**의 수기 구간은 안 보인다 (분할을 요청하는 이유).
5. **보고서·연결 지도(M4)**: 파트 매트릭스 23×23 이 기본, '담당 부서' 로 묶어 보기(10 그룹)를 옵션으로.
6. **골든 영향**: 합성 데이터는 지금 '파일 분야 = 담당 부서 값'(10개 체계)이다. parts.yaml 에 합성용 파트(약칭 = 분야명)를 넣어
   골든 값(Feed 71·대조 103행·착수 15행)을 그대로 유지하고, v1.1 형식 합성 파일 1개는 약칭 파일명으로 추가한다.
